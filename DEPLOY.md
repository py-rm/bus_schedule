# Развёртывание и автоматизация

Как автоматизировать парсеры расписаний и новостей в облаке так, чтобы
приложение получало свежие JSON-файлы, не выходя за бесплатные лимиты.

---

## 1. Назначение облака

Проект состоит из двух частей:

1. **Парсеры** (`orenburg_dacha_parser.py`, `dacha_news_parser.py`). Запускаются
   вручную. Для автообновления нужен запуск по расписанию.
2. **Android-приложение**, которое читает готовые JSON-файлы по ссылке.

Облако решает две задачи:
- запускает парсеры по расписанию (автоматически);
- хранит готовые JSON в интернете, чтобы приложение скачивало их по ссылке.

Порядок работ: сначала делается приложение (MVP), облако подключается позже,
перед релизом, для автообновления. Подробнее — раздел 9.

---

## 2. Общая схема

```
        ┌─────────────────────────────────────────────┐
        │            ЯНДЕКС ОБЛАКО                     │
        │                                             │
        │  Cloud Functions (запуск парсеров)           │
        │  ┌───────────────────────────────────────┐   │
        │  │  парсер новостей    — 1 раз в день    │   │
        │  │  парсер расписаний  — 1–2 раза в день │   │
        │  └───────────────┬───────────────────────┘   │
        │                  │  пишут JSON               │
        │                  ▼                           │
        │  Object Storage (хранилище JSON, публичное)  │
        │     dacha_news.json                          │
        │     dacha_schedule.json                      │
        │                                             │
        │  после парсинга: если изменилось — пуш      │
        └───────────────┬─────────────────────────────┘
                        │  публичные ссылки на JSON
                        ▼
              ANDROID-ПРИЛОЖЕНИЕ
```

---

## 3. Cloud Functions

Cloud Function — Python-код, выполняемый в облаке по триггеру (например, по
расписанию / CRON). В функцию загружаются код парсера и библиотека `requests`.

Расписание запусков: новости 1 раз/день; расписание 1–2 раза/день весной и
осенью, зимой не запускать (маршруты не ходят).

---

## 4. Бесплатные лимиты Яндекс Облака (официальные данные)

Лимиты действуют на календарный месяц. Неизрасходованный остаток обнуляется
в конце месяца.

### Cloud Functions — бесплатно в месяц:
| Показатель | Лимит | Реальная нагрузка |
|-----------|-------|-------------------|
| Вызовы | 1 000 000 | ~60–90 |
| Время вычислений | 10 ГБ·час | доля процента |

При парсере на 128 МБ и ~30 сек работы расход за один запуск ≈ 0.001 ГБ·час.
Даже при двух запусках в день за месяц ≈ 0.06 ГБ·час (менее 1% лимита).

### Object Storage — бесплатно в месяц:
| Показатель | Лимит | Реальная нагрузка |
|-----------|-------|-------------------|
| Хранилище | 1 ГБ | < 1 МБ |
| Записи (PUT/POST/PATCH/LIST) | 10 000 | ~60 |
| Чтения (GET/HEAD/OPTIONS) | 100 000 | сотни–тысячи |

Записи делаются только при изменении данных (по MD5). Выход за лимит чтения
возможен только при быстром росте аудитории; при скачивании «по пушу» лимит
покрывает тысячи активных пользователей.

---

## 5. Раздача JSON приложению

В Object Storage создаётся бакет и делается публичным. JSON доступен по ссылке:

```
https://storage.yandexcloud.net/dacha-app/dacha_schedule.json
https://storage.yandexcloud.net/dacha-app/dacha_news.json
```

Приложение скачивает файл по ссылке. API Gateway и Cloud CDN:
- **API Gateway** — не требуется. Он не увеличивает лимит запросов
  (100 000/мес, как и у Object Storage) и лишь перенаправляет трафик.
- **Cloud CDN** — платный, на старте не требуется. Аудитория локальная,
  лимита чтения достаточно.

### Важно про лимит чтения (GET) — не тянуть большой JSON при каждом запуске
Лимит чтения Object Storage — **100 000 GET/мес**. Если приложение будет
качать `dacha_schedule.json` (сотни КБ) при **каждом запуске** — на тысячах
пользователей легко упереться в лимит:
- 300 польз. × 1 запуск/день × 30 = 9 000 (ок);
- 3 000 польз. × 1 запуск/день × 30 = 90 000 (почти предел);
- при 2–3 запусках/день — выход за лимит.

Поэтому приложение **не должно гонять полное расписание при каждом открытии.**
Варианты (выбор — на этапе разработки приложения):
- **Кэшировать** расписание на устройстве, обновлять по пушу / редкой
  авто-проверке (как в разделе 7), а не при каждом запуске;
- для проверки обновлений версии приложения использовать **отдельный крошечный
  файл-метку версии** (около 200 байт), а не большой JSON расписания.

Это согласуется с общим принципом из раздела 6–7: скачивание по пушу / редко,
чтобы не жечь лимит чтения на тысячи активных пользователей.

## 6. Пуш-уведомления

Пуш — сообщение, доставляемое на телефон даже при закрытом приложении.
Приложение само не опрашивает сервер постоянно; оно скачивает JSON только
после прихода пуша либо по редкой авто-проверке.

### Каналы
| Магазин | Канал |
|---------|-------|
| Google Play | FCM (Firebase Cloud Messaging) |
| ruStore | RuStore Push (VK) — на устройствах без Google-сервисов FCM не гарантирован |

FCM бесплатен, лимиты велики. Облачная функция шлёт пуш в оба канала.

### Условие отправки
Парсер сравнивает новое значение MD5/номера новости со старым:
- совпало — ничего не изменилось, пуш не шлётся;
- разошлось — пуш «расписание/новость обновились».

### Обновление версии приложения — по пушу
**Решение:** обновление версии android-приложения идёт **по пуш-уведомлению**.
При выходе новой версии приложения облачная функция шлёт пуш с номером
актуальной версии; приложение сравнивает его со своей установленной версией
и при необходимости показывает «вышла новая версия, обновите» (или блокировку
по дате — см. NOTES.md).

Это решает и вопрос обновления, и лимит чтения Object Storage: проверка версии
идёт через пуш (мимо Object Storage и его 100 000 GET/мес), отдельные
скачивания файлов для сверки версии не требуются. Пуш-инфраструктура (та же,
что для новостей) закрывает и обновление расписания, и обновление приложения.

### Нюансы
- Пуш не гарантирован (телефон выключен, без сети) — нужна авто-проверка.
- Пуши отправлять только при реальном изменении, не чаще.
- Для адресной отправки нужно получить токен устройства при первом запуске.

---

## 7. Фоновая авто-проверка

Страховка на случай недоставленного пуша. Выполняется в сезоны изменений
расписания: весна (середина апреля – середина июня) и осень (середина августа
– конец октября). В остальное время — только по пушу.

Реализация: приложение раз в сутки в сезон запрашивает JSON, сравнивает MD5
с загруженным; при изменении скачивает новый файл. Механизм — WorkManager
для Android.

## 8. Защита от битых данных (шлюз перед публикацией)

Перед публикацией JSON в Object Storage должен проходить проверку
`schema_check.py`. Это страховка: если на сайте изменится вёрстка, парсер
сломается или придёт битый JSON — в приложение ничего «плохого» не уйдёт.

Пайплайн внутри одной Cloud Function (код проверки — отдельный модуль,
но выполняется как шаг той же функции, отдельную Cloud Function не создаём):

```
парсер → schema_check --expected <N>
            │
            ├─ код 0 (OK)      → публиковать JSON → (пуши при изменении)
            ├─ код 2 (WARN)    → публиковать JSON → уведомить администратора
            └─ код 1 (ERROR)   → НЕ публиковать → уведомить администратора
```

- **WARN** (маршрутов стало меньше на 1–3): продолжаем, но администратор узнаёт.
- **ERROR** (маршрутов меньше более чем на 3, повреждён JSON и пр.): предыдущая
  удачная версия остаётся в storage, битый не перезаписывает её.

Число-эталон `--expected <N>` берётся из настройки Cloud Function (сколько
маршрутов должно быть, сейчас 41). Если «эталон» неизвестен — храни его
в переменной окружения функции, а не зашивай в код.

### Уведомление администратора об ошибке
Уведомление — **исходящий** запрос из Cloud Function (HTTP через `requests`),
API Gateway для этого **не нужен** (он лишь принимает входящие запросы).

Каналы (с учётом доступности в РФ):
- **Основной — письмо на почту (SMTP)**: Яндекс.Почта / Gmail. Бесплатно,
  надёжно, не блокируется; на телефоне приходит уведомление.
- **Запасной/удобный — Telegram-бот**: быстрый просмотр, но в РФ может не
  дойти (мессенджер ограничен), поэтому только как дубль, не полагаться.

Отправлять уведомление при любом коде, отличном от 0 (и при WARN, и при ERROR),
с текстом: что проверялось, какой код возврата, какие ошибки/замечания.

## 9. Шаги настройки

1. Создать аккаунт Яндекс Облака (free tier).
2. Создать бакет в Object Storage, сделать публичным.
3. Адаптировать парсеры: сохранение JSON в Object Storage (библиотека
   `boto3`/s3-API) вместо локальной папки.
4. Создать Cloud Functions и триггеры по расписанию. Внутри функции:
   парсер → `schema_check --expected <N>` → публикация по коду возврата.
5. Настроить отправку пуша при изменении данных (FCM + RuStore Push).
6. В приложении: получение токена, обработка пуша, сезонная авто-проверка.
7. Настроить уведомление администратора об ошибке (SMTP-почта + Telegram-бот).

## 10. Порядок работ по проекту

1. Приложение (MVP): экран расписания, чтение локального JSON.
2. Виджет.
3. Облако (функции + storage) для автообновления.
4. Пуши.
5. Реклама.
6. Публикация в Google Play, затем по желанию ruStore.

Облако настраивается после приложения, перед релизом.

## 11. Формат данных JSON

JSON-файлы (`dacha_schedule.json`, `dacha_news.json`) — единый источник для
Android-приложения и настольного просмотрщика (`schedule_viewer.py`, собран
в `DachaScheduleViewer.exe`). Приложение опирается на эти форматы:

- Время в расписании всегда хранится в формате `HH:MM` (например `08:00`).
  Парсер принимает время и с точкой (`8.00`), и с двоеточием (`8:00`),
  с одной цифрой в часах/минутах и приводит к единому виду с ведущим нулём —
  сайт заполняют вручную, стиль у редакторов разный.
- Блок расписания: `days` (ограничение по дням), `valid_from` (с какой даты
  действует), `note` (пометка-подзаголовок, необязательно), `stops` (пункты
  и времена).
- Пометка `note` (например «в том числе рейсы ... до с/о Гребени:») выделяется
  в отдельный блок расписания перед своими рейсами — так она отображается
  корректно и на сайте, и в приложениях.
- Просмотрщик показывает и новость: внизу главного окна — карточка последней
  новости из `dacha_news.json` (клик открывает полную новость со ссылкой на
  источник). Если файла нет — карточка просто скрывается.
- Перед публикацией данных запускайте `python schema_check.py` (находится
  в папке проекта): код 0 — всё чисто, ошибки — список проблем и код 1.
  Проверяет структуру, MD5, формат и порядок времени, поля новости. Это
  страховка для Cloud Functions: публиковать JSON только после успешной
  проверки.

## 12. Примечания

- Встраивать парсеры в приложение не нужно: это нагрузка на муниципальный сайт
  и сложность для Android. Парсер выполняется в облаке один раз на всех.
- Ручную кнопку «обновить» в приложении лучше не делать постоянной; основное
  обновление — по пушу и авто-проверке.
