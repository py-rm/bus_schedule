# Заметки по проекту (принятые решения и контекст)

Файл фиксирует решения и контекст, чтобы новая сессия могла продолжить работу
без потери информации. Референс по парсерам и JSON — в `README.md`,
архитектура облака и лимиты — в `DEPLOY.md`.

## Суть проекта
- Сезонные дачные (садоводческие) автобусные маршруты Оренбурга.
- Парсеры выгружают расписание и последнюю новость об изменениях в JSON.
- Цель: Android-приложение (виджет + окно с расписанием) для дачников
  (в основном пенсионеры) и людей без автомобиля.

## Текущий статус
- Готовы и проверены оба парсера (Python):
  - `orenburg_dacha_parser.py` -> `dacha_schedule.json` (41 маршрут);
  - `dacha_news_parser.py` -> `dacha_news.json` (последняя новость из RSS).
- JSON прочитан приложением-заготовкой (структура описана в README).
- Готов настольный просмотрщик `schedule_viewer.py` (tkinter), собран
  в `dist/DachaScheduleViewer.exe` — для проверки расписания на ПК.
- Готов первый QA-инструмент `schema_check.py` — проверка качества JSON
  (структура, MD5, времена, поля новости). Доработан под облако:
  трёхуровневый код возврата + порог по числу маршрутов (см. ниже).
- Облако ещё не настроено, парсеры запускаются вручную.

## Настольный просмотрщик (Windows)
- `schedule_viewer.py` — tkinter-программа для проверки JSON на компьютере;
  собран в `dist/DachaScheduleViewer.exe` (PyInstaller, onefile/windowed).
- Кладётся рядом с `dacha_schedule.json` и `dacha_news.json`.
- Сетка маршрутов + поиск; клик по номеру — окно маршрута (дни, перевозчик,
  блоки, MD5). Внизу главного окна — карточка последней новости из
  `dacha_news.json` (клик открывает полную новость со ссылкой на источник).
- Сборка .exe: `python -m PyInstaller --onefile --windowed --name
  DachaScheduleViewer --noconfirm schedule_viewer.py`

## Особенности данных сайта (важно для парсинга)
- Расписание заполняют вручную разные редакторы, стиль разный:
  - время бывает и `8.00`, и `8:00`, и `7:5` — парсер приводит всё к `HH:MM`
    с ведущим нулём (`08:00`);
  - дата «с 01.09.2026» свёрстана с пробелами внутри цифр (`с 0 1.09.202 6:`) —
    парсер чистит пробелы;
  - «Рабочие дни» — допустимый маркер дней наравне с «Выходные»/«Будни».
- Пометка к рейсам (например «в том числе ... до с/о Гребени:») хранится как
  `note` отдельного блока расписания — она описывает именно свои рейсы,
  а не весь график.

## Проверка данных (QA-инструмент)
- `schema_check.py` — разовый прогон после пересбора JSON
  (`python schema_check.py`), проверяет `dacha_schedule.json` и
  `dacha_news.json` из своей папки (или по `--schedule` / `--news`).
- Проверки: совпадение `routes_count`, уникальность номеров, непустые поля,
  пересчёт MD5 (маршрутов и файлов — по той же логике, что в парсерах),
  наличие остановок, дата `ДД.ММ.ГГГГ`, времена `HH:MM` в пределах суток
  без повторов и по возрастанию, поля новости.
- Итог «ОШИБОК: N / ЗАМЕЧАНИЙ: M».
- Проверен на испорченных файлах: все заложенные ошибки обнаруживаются.
- **Доработка для облака (готово):** трёхуровневый код возврата
  `0`=OK / `2`=WARN / `1`=ERROR. Параметр `--expected <N>` — эталон числа
  маршрутов: если стало меньше на 1–3 — WARN (продолжаем, но уведомить),
  если больше чем на 3 — ERROR (стоп, оставить старый файл + уведомить).
  Без `--expected` — только проверка структуры (как раньше).
- В облаке выполняется как **шаг той же Cloud Function** (код отдельным
  модулем, но не отдельной функцией), служит «шлюзом» перед публикацией.
  Подробнее — `DEPLOY.md`, раздел 8.

## Уведомление администратора об ошибке (принятое решение)
- Канал — **исходящий** запрос из Cloud Function (HTTP через `requests`).
- **API Gateway НЕ нужен** для уведомлений: он принимает входящие запросы,
  а уведомление — исходящее событие. Отвергнут.
- Основной канал: **письмо на почту (SMTP)** — Яндекс.Почта/Gmail, бесплатно,
  в РФ не блокируется, надёжно.
- Запасной/удобный: **Telegram-бот** — только как дубль, в РФ мессенджер
  ограничен, не полагаться.
- Слать при любом коде, отличном от 0 (и WARN, и ERROR): что проверялось,
  код возврата, список ошибок/замечаний.

## Платформы приложения
- **ruStore — приоритет, запуск первым.** Причины: аудитория (дачники-пенсионеры
  РФ) — у многих телефоны без Google-сервисов (Xiaomi/Realme/Honor с росс.
  прошивками), ruStore на них родной и работает без VPN; публикация бесплатная,
  нет $25 и проблем с оплатой российской картой; юрисдикция РФ.
- **Google Play — позже**, когда решится вопрос оплаты аккаунта ($25; российской
  картой напрямую сейчас не оплатить — карты Visa/Mastercard РФ не принимаются,
  MIR тоже; нужна зарубежная карта). Это не срочно.
- Распространение среди аудитории — через **ruStore и/или прямой APK** (без VPN,
  без Google-сервисов). iOS не нужен (целевая аудитория — Android).

## Технология приложения
- **Flutter (Dart), НЕ nocode.** Причины: продукт серьёзный и на годы, код остаётся
  нашим, есть ИИ-ассистент который пишет код (снимает главное возражение nocode).
- Структура по вкладкам: «Расписание» (маршруты, время рейсов) и «Дачный клуб»
  (контентная вкладка).
- **Виджет — ОТДЕЛЬНЫМ вторым релизом**, не на старте. Самый сложный технически
  компонент (нативная часть на Kotlin + Glance / библиотека home_widget), плюс
  может уменьшать заходы в приложение (а значит показы рекламы). Сначала
  полноценное приложение, потом виджет.
- **Порядок релизов:** MVP «Расписание» → «Дачный клуб» с рекламой → виджет.

## Реклама (принятый план)
- Главный доход для провинции: **прямые локальные рекламодатели** —
  питомники саженцев, доставка перегноя/земли/щебня, бурение скважин,
  садовый инвентарь. Продажа места за фикс/период. **Без SDK** — свои
  рекламные карточки внутри приложения. Это основа заработка.
- Сетевые мобильные SDK (**Yandex Mobile Ads / РСЯ**) на старте НЕ подключаем:
  на малой локальной аудитории доход копеечный (аукцион не работает на
  сотнях пользователей), лишний вес и политики. Подключаем, когда появится
  аудитория (этап после MVP).
- **РСЯ (Рекламная сеть Яндекса) работает и в нативном мобильном SDK —
  веб/WebView НЕ обязателен.** Уточнение (актуально на 2026): контекстная
  реклама и форматы приложений доступны через **Yandex Mobile Ads SDK**
  нативно (во Flutter — плагин `yandex_ads`). Ниже — два наших формата.
- **Формат 1 — лента (Feed) во вкладке «Дачный клуб».** Лента-рекомендации
  со статьями/объявлениями по интересам (дача, кулинария, стройка) — аналог
  рекомендаций в браузере. Интегрируется нативно через SDK, формат доступен
  только для Android-приложений. WebView и хостинг веб-страницы не нужны.
- **Вкладка «Дачный клуб» НЕ должна быть пустой обёрткой под одну ленту.**
  Приложение святое правило РСЯ (п.1.1m): нельзя подключать Ресурс,
  «основной целью которого является показ рекламы». Отдельная вкладка
  отдельным ресурсом не является (ресурс — всё приложение, его цель —
  расписание), но РСЯ (п.6 «реклама не должна преобладать над содержанием»)
  и модерация RuStore («приложение должно быть самоценным») могут забраковать
  вкладку, где лента занимает всё и нет своего содержания. Поэтому поверх
  ленты держим **собственный контент**: заголовок, вступительный текст про
  тематику (дача, кулинария, стройка), рубрики/разделы. Лента идёт ниже.
  Это закрывает и «преобладание рекламы», и требование «самоценности».
- **Формат 2 — native-баннер на странице «Расписание».** Рекламный баннер,
  обновляющий объявление каждые 30–40 сек. Нативно через SDK.
- **Ограничение РСЯ (важно):** блок на одном экране **не должен перезагружаться
  чаще одного раза в 30 секунд**. План 30–40 сек допустим (не реже 30),
  брать ~30–45 сек, не ниже 30.
- **Условие монетизации РСЯ (важно):** статус партнёра — **самозанятый, ИП
  или юрлицо** (обычное физлицо не может). Оферта РСЯ от 15.07.2026 определяет
  «Партнёра» только так. Поэтому РСЯ-лента и баннер подключаются **после
  оформления самозанятости**, когда появится аудитория.
- Реклама РСЯ должна быть маркирована («Реклама», возрастная метка, домен) —
  добавляется автоматически, не редактировать. Рекламы не должно быть слишком
  много (не мешать использованию).
- Запасной канал: **VK Реклама / MyTarget** (особенно для ruStore).
- Позже: **премиум «без рекламы»** (при появлении молодой аудитории).
- **Отброшено (неактуально для маленького городского приложения):**
  партнёрка такси, доставка еды, барахолка (C2C).

## Пуши
- Два канала: FCM (Google Play) + RuStore Push (ruStore).
- Слать только при реальном изменении данных (сравнение MD5/news_id).
- Пуш не гарантирован (телефон офлайн) — нужна авто-проверка.

## Обновление данных в приложении
- Основной канал: скачивание JSON по пушу (редко, только при изменении).
- Страховка: авто-проверка MD5 в сезоны изменений (весной и осенью).
- Ручную кнопку «обновить» постоянной не делать (экономия лимитов).

## Обновление самого android-приложения и принудительная замена MVP (финальная схема)
Долгосрочный план: **MVP-приложение живёт только до сезона-2027**, затем
принудительно заменяется на завершённое приложение (с пушами, авто-обновлением
и рекламой). Это защита монетизации: никто не «останется кайфовать» на старом
бесплатном MVP.

**Дедлайн блокировки: март 2027.** К февралю 2027 готово новое «полное»
приложение (пуши, автоматическое обновление, реклама).

**Механизм блокировки в старом MVP (двойная проверка, работает офлайн):**
1. **Проверка 1 — дата смартфона против дедлайна.** Если дата устройства
   >= дедлайна (март 2027) → заблокировать: экран «требуется обновление»
   + кнопка установки нового приложения, расписание не открывается.
2. **Проверка 2 — анти-обман (против отката даты на телефоне).** Если
   человек намеренно отмотал дату телефона назад — сравниваем дату
   смартфона с **датой `generated_at` внутри последнего скачанного JSON**
   (расписание/новость). Если дата смартфона РАНЬШЕ, чем `generated_at`
   (телефон «в прошлом» относительно реально собранных в облаке данных) —
   это признак обмана → блокируем + плашка.

**Важные уточнения:**
- Анти-обман считаем по **`generated_at` (дата внутри JSON), а НЕ по дате
  скачивания файла на телефон** — дату скачивания легко подделать откатом
  часов, а `generated_at` внутри файла подделать сменой даты устройства нельзя.
- Зимой расписание не обновляется (маршруты не ходят) — `generated_at` стоит
  с осени. Это НОРМАЛЬНО: дата смартфона позже `generated_at` не является
  обманом (блокируем только когда смартфон РАНЬШЕ `generated_at`). Проверка 2
  срабатывает именно на «телефон в прошлом», а не на «в данные давно не
  обновлялись».
- До марта-2027: мягкое/умеренное напоминание «вышла новая версия» (без
  навязчивости). После дедлайна — жёсткая блокировка.
- Приложение требует интернета (расписание обновляется из сети), поэтому
  проверка срабатывает при каждом открытии.
- **Заложить с самого начала в MVP**, чтобы не переделывать.

**Как приходит уведомление о новой версии (решение):** обновление версии
приложения — **по пуш-уведомлению**. При выходе новой версии облачная функция
шлёт пуш с номером версии; приложение сравнивает со своей и сообщает/блокирует.
Это не тратит лимит чтения Object Storage (проверка идёт мимо него). (Детали —
в `DEPLOY.md`, раздел 6.)

**Не решено (на другой день):** технические методы реализации для MVP
(как именно MVP без пушей узнаёт о новой версии) и конкретные способы
экономии/реализации проверки. Пока открыто.

## Продвижение и распространение (план)
- **Каналы — мессенджеры: MAX (основной), WhatsApp, Telegram.** Не VK-группы.
  Целевая аудитория (дачники-пенсионеры) сидит именно там; у многих телефоны
  без Google-сервисов, поэтому MAX нативно (без VPN), а WhatsApp/Telegram
  требуют обхода — что пожилым неудобно. Отсюда: распространяем через
  **ruStore и/или прямой APK — без VPN и без Google-сервисов**.
- Идём **через председателей СНТ** (по сути админы дачных чатов): списаться,
  попросить **опубликовать и закрепить** в топе пост с приложением. У них
  доверие — высокая конверсия и меньше риска «спама».
- **Материалы:** презентационный пост + видеоролик (CapCut) + картинки.
  Видео — 30–60 сек, крупные подписи (работает без звука), загружать нативно
  в канал. Ссылка на установку «в 2 тапа», простая подача для пенсионера.
- **Сезонный посыл:** «пока осень-зима — установите и протестируйте на своих
  телефонах; к новому дачному сезону получите отлаженное приложение».
  Это и тесты всю зиму, и обещание ценности пользователям.
- **Сбор замечаний/предложений** от тестеров — записывать в таблицу,
  закладывать в развитие проекта.

## Логирование и диагностика (принятое решение)
- **Логирование в приложении — закладываем с самого начала.** Приложение
  пишет логи (ошибки, события) так, чтобы их можно было собрать.
- Для тестового сезона и продакшена: подключить **сервис сбора крашей/ошибок**
  (Sentry или AppMetrica от Яндекса) — приложение само шлёт отчёт при ошибке
  (какое устройство, версия, стек-трейс). Это решает задачу «ошибка, которую
  нашли через год» — она сама приезжает к разработчику.
- Присылаемую пользователем информацию («что-то съехало/пропало») можно
  дополнять логами — они помогают мне точнее диагностировать.
- Полная «автоматизация отладки» (я сам нахожу-чиню-запускаю без участия)
  сейчас не делается; практичная схема: логи → анализ (мной) → правка →
  сборка → проверка на устройстве.

## Ориентиры по аудитории и нагрузке (оценочно)

- Потенциальная аудитория сезона — тысячи человек.

- Ориентир дохода: десятки тысяч руб/мес в сезон (РСЯ + прямые продажи).
- Лимиты free tier покрывают нагрузку с запасом (см. DEPLOY.md).
